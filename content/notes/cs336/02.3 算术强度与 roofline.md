# 02.3 算术强度与 roofline

出处：CS336 第 2 讲（Percy Liang），`arithmetic_intensity` 与 `roofline_plots` 两节；GeLU 融合的数据取自第 6 讲 trace。所属栏目：[[notes/cs336/index|CS336：从零构建语言模型]]。

**术语预备**
- **HBM / 显存**：GPU 上的大容量内存（H100 有 80 GB）。数据平时放在这里，计算单元要用时得先搬过去，算完再搬回来。
- **带宽（bandwidth）**：每秒能搬多少字节。H100 的 HBM 是 $3.35\times10^{12}$ 字节/秒，也就是 3.35 TB/s。
- **算术强度（arithmetic intensity）**：一个运算的 FLOPs 除以它要搬的字节数，单位 FLOP/字节。这是运算自身的属性。
- **加速器强度（accelerator intensity）**：硬件的峰值 FLOP/s 除以带宽，也是 FLOP/字节。这是硬件的属性。
- **带宽受限 / 算力受限（memory-bound / compute-bound）**：时间主要花在搬数据上 / 花在算上。
- **kernel**：GPU 上执行的一个函数。PyTorch 里每个运算通常对应一个或几个 kernel。

## 0. 问题：MFU 为什么到不了 1

[[02.2 数 FLOPs：矩阵乘法的 2mnk 与 MFU]] 留下了一个问题：同一块 GPU，有的运算能跑到峰值的 80%，有的连 1% 都不到。讲义给的第一个解释是：计算不只是"算"，还要"搬"。

讲义的模型：做一次运算分三步，(1) 把输入从显存搬到计算单元，(2) 算，(3) 把结果搬回显存。假设搬和算可以完全重叠，那么

$$\text{时间}=\max\Big(\underbrace{\frac{\text{字节数}}{\text{带宽}}}_{\text{搬}},\ \underbrace{\frac{\text{FLOPs}}{\text{峰值}}}_{\text{算}}\Big).$$

哪一项大，运算就受哪一项限制。

## 1. 一个比值决定卡在哪

两项相比：

$$\frac{\text{FLOPs}/\text{峰值}}{\text{字节数}/\text{带宽}}=\frac{\text{FLOPs}/\text{字节数}}{\text{峰值}/\text{带宽}}=\frac{\text{算术强度}}{\text{加速器强度}}.$$

所以只要比两个数：
- **算术强度**：这个运算每搬 1 字节，要做多少 FLOPs。
- **加速器强度**：这块硬件每搬 1 字节的时间里，能做多少 FLOPs。

H100 的 bf16 加速器强度是 $989\times10^{12}/3.35\times10^{12}=295$ FLOP/字节。一个运算每搬 1 字节如果做不到 295 次运算，计算单元就会闲着等数据。

由此直接得到 MFU 的上界。实际速度 = FLOPs/时间 = $\min(\text{峰值},\ \text{算术强度}\times\text{带宽})$，除以峰值：

$$\text{MFU}\le\min\Big(1,\ \frac{\text{算术强度}}{\text{加速器强度}}\Big).$$

这就是讲义最后那句 "MFU = min(1, arithmetic-intensity / accelerator-intensity)"。说它是上界，是因为模型里还没算固定开销、通信这些东西。

## 2. 各种运算的算术强度

讲义逐个算了一遍，都按 bf16（每个数 2 字节）：

| 运算 | FLOPs | 搬的字节 | 算术强度 | MFU 上界（H100） |
|---|---|---|---|---|
| ReLU，长 $n$ 的向量 | $n$ | 读 $2n$，写 $2n$ | 1/4 | 0.08% |
| GeLU | 约 $20n$ | $4n$ | 5 | 1.7% |
| 内积 $x\cdot w$ | $2n$ | 读两个向量 $4n$ | 1/2 | 0.17% |
| 矩阵乘向量 $n\times n$ | $2n^2$ | 主要是读矩阵 $2n^2$ | 1 | 0.34% |
| 矩阵乘矩阵 $n\times n$ | $2n^3$ | 读两个、写一个 $6n^2$ | $n/3$ | $n\ge886$ 时 100% |

前四个都是带宽受限，而且差得很远。讲义里的 ReLU 例子（$n=2^{20}$）：搬数据要 1.25 微秒，算只要 1.06 纳秒，差了一千多倍。

只有矩阵乘矩阵的算术强度会随规模增长：$n=1024$ 时是 341，超过 295，"Finally, compute-bound!"。原因很简单：$n\times n$ 的矩阵乘法读进来 $2n^2$ 个数，却要做 $2n^3$ 次运算，每个数平均被用了 $n$ 次。其他运算里，每个数读进来只用一两次。

### 一个统一的公式

一般地，$m\times k$ 乘 $k\times n$，bf16 下要做 $2mkn$ FLOPs，搬 $2(mk+kn+mn)$ 字节，所以

$$\text{算术强度}=\frac{mkn}{mk+kn+mn}=\frac{1}{\frac1m+\frac1k+\frac1n}.$$

这个式子和并联电阻的公式一样：结果由三个维度里**最小的那个**主导。方阵时三个都是 $n$，得到 $n/3$；矩阵乘向量时有一个维度是 1，算术强度就被压到 1 附近。

## 3. 最重要的推论：一次要有几百个 token

在 Transformer 里，权重矩阵是 $D\times D$（$D$ 是几千），一次喂进去的是 $B$ 个 token 的向量，组成 $B\times D$ 的矩阵。代入上面的公式：

$$\text{算术强度}=\frac{1}{\frac1B+\frac2D}\approx B\qquad(B\ll D).$$

**算术强度约等于一次一起算的 token 数。** 要在 H100 上达到算力受限，$B$ 要超过 295。精确地解 $1/B+2/D=1/295$：$D=4096$ 时 $B\ge345$，$D=8192$ 时 $B\ge318$。

| 一起算的 token 数 $B$（$D=4096$） | 1 | 8 | 64 | 256 | 1024 |
|---|---|---|---|---|---|
| 算术强度 | 1.0 | 8.0 | 62 | 228 | 683 |

这就是讲义说的：
- **训练是算力受限的.** 一个 batch 有十几到几百条序列，每条几千个 token，同一个权重矩阵一次要乘几万到几百万个 token。
- **推理是带宽受限的.** 逐个生成 token 时，每条序列每一步只有 1 个新 token。如果同时只服务几个用户，$B$ 就是个位数，这时就是矩阵乘向量，每生成一个 token 都要把整个模型的权重从显存里读一遍，计算单元几乎全在等。推理系统要把很多用户的请求拼成一个 batch，原因就在这里（[[10.1 prefill 与 decode：为什么 decode 卡在带宽]]）。

## 4. 精度越低，越难算力受限

讲义提了一句："arithmetic/accelerator intensity also depends on the precision"。可以具体算一下 H100 上的方阵乘法：

| 格式 | 峰值 | 加速器强度 | 方阵乘法的算术强度 | 算力受限需要 |
|---|---|---|---|---|
| fp32 | 67.5 TFLOP/s | 20 | $2n^3/(3\cdot4n^2)=n/6$ | $n\ge121$ |
| bf16 | 989 TFLOP/s | 295 | $n/3$ | $n\ge886$ |

换成 bf16，每个数的字节减半，算术强度翻倍；但峰值涨了将近 15 倍，加速器强度也跟着涨了 15 倍。所以 bf16 下要更大的矩阵才能喂饱。fp8 的峰值又翻一倍，门槛还要再高。

硬件一代代也在往这个方向走（第 5 讲第 18 页："compute scaling is faster than memory scaling"）。按规格表算 bf16 的加速器强度：

| GPU | bf16/fp16 稠密峰值 | 带宽 | 加速器强度 |
|---|---|---|---|
| V100 | 125 TFLOP/s | 0.9 TB/s | 139 |
| A100 (80GB) | 312 TFLOP/s | 2.0 TB/s | 153 |
| H100 | 989 TFLOP/s | 3.35 TB/s | 295 |
| B200 | 2250 TFLOP/s | 8 TB/s | 281 |

越往后，越需要大矩阵、大 batch，也越需要想办法少搬数据。

## 5. 带宽受限时，FLOPs 几乎是免费的

一个运算如果带宽受限，多做一些计算并不会变慢，因为计算单元本来就在闲着。讲义的说法："ReLU is not faster than GeLU (when doing things in an isolated way)"。

在一台普通 CPU 上也能看到（2 核，实测矩阵乘法约 270 GFLOP/s，搬数据约 23 GB/s，加速器强度约 12）。对 $2^{26}$ 个 fp32 数各做一次运算，读 256 MB、写 256 MB：

| 运算 | 每个元素大约多少 FLOPs | 时间 |
|---|---|---|
| 复制 $y=x$ | 0 | 23.3 ms |
| ReLU | 1 | 23.7 ms |
| $2x$ | 1 | 23.3 ms |
| $e^x$ | 十几 | 24.3 ms |
| $\sin x$ | 十几 | 26.9 ms |
| GeLU（erf 版） | 几十 | 26.8 ms |

不管算什么，时间都约等于把 512 MB 搬一遍的时间。

也有一个例外：tanh 版 GeLU 用了约 100 ms。单独算 tanh 只要 25 ms，tanh 版 GeLU 只比它多几次乘加，却慢了 4 倍。说明 PyTorch 在 CPU 上的这个实现实际执行的指令远多于公式里的 FLOPs，它就不再是带宽受限了。算术强度要按实际执行的运算算，不能只看公式。

**反过来，省搬运才是关键：算子融合.** 第 6 讲把 GeLU 的公式 $0.5x(1+\tanh(0.798(x+0.0447x^3)))$ 直接用 PyTorch 写出来，会变成 9 个左右的 kernel：每一个乘、加、tanh 都是一次"从显存读进来、算一下、写回显存"。PyTorch 内置的 GeLU 是一个 kernel，读一次、写一次。在 B200 上对 $16384\times16384$ 的矩阵：

| 实现 | 时间 |
|---|---|
| 公式直接写（多个 kernel） | 3.83 ms |
| PyTorch 内置（一个 kernel） | 0.73 ms |
| `torch.compile` 自动融合 | 1.08 ms |

FLOPs 完全一样，只是搬运次数不同，时间差了 5 倍。更进一步，把 GeLU 直接融合进前面那个矩阵乘法，趁结果还在片上就做完，GeLU 就几乎不花时间（[[05.3 让 GPU 跑快的几招：低精度、算子融合、重计算、合并访存]]）。

## 6. roofline 图

把 §1 的式子画成图：横轴是算术强度（对数），纵轴是能达到的 FLOP/s（对数）。

$$\text{能达到的 FLOP/s}=\min(\text{峰值},\ \text{算术强度}\times\text{带宽}).$$

图形是一条先斜着上升、再变平的折线，像一个屋顶，roofline 的名字就从这里来：
- 左边斜坡：带宽受限，速度 = 算术强度 × 带宽，斜率为 1。
- 右边平顶：算力受限，速度 = 峰值。
- 拐点的横坐标正好是加速器强度（H100 bf16 是 295）。

讲义的读法：横轴上的每一个位置是一种运算，每一条折线是一种硬件。拿到一个运算，算出它的算术强度，在图上往上找，碰到哪条线，那就是这块硬件上它能跑到的最快速度。

**roofline 只是上界.** [[02.2 数 FLOPs：矩阵乘法的 2mnk 与 MFU]] 里第 6 讲的那组 B200 测量（fp32 方阵乘法）：B200 的 fp32 加速器强度大约是 $75/8\approx9$，方阵乘法 $n\ge57$ 就该算力受限。实测 $n=1024$ 时 MFU 只有 4%，那里卡住的是 0.7 毫秒的固定开销，roofline 模型里没有这一项。$n=8192$ 时是 83% 而不是 100%，差的那部分是分块方式、显存对齐这些细节（第 5 讲）。roofline 告诉你天花板在哪，以及该往哪个方向优化，但不保证能碰到天花板。

## 7. 总表

| 情形 | 算术强度 | 结论 |
|---|---|---|
| 逐元素运算（ReLU、GeLU、norm、残差加法） | 1 左右或更低 | 永远带宽受限，FLOPs 多少不要紧，要紧的是少搬：融合 |
| 矩阵乘向量（推理逐 token 生成，batch 小） | ≈ 1 | 带宽受限，要把很多请求拼成一个 batch |
| $B$ 个 token 乘 $D\times D$ 权重 | $\approx B$ | $B\gtrsim300$ 才算力受限（H100 bf16） |
| 大方阵乘法 | $n/3$ | $n\gtrsim900$ 算力受限 |
| 换成更低精度 | 翻倍 | 但硬件强度涨得更多，门槛更高 |

一句话：时间取"搬"和"算"里慢的那个，比较"运算每字节做多少 FLOPs"和"硬件每字节能做多少 FLOPs"就知道卡在哪；H100 上这个门槛是 295，矩阵乘法要一次喂几百个 token 才过得去，逐元素运算永远过不去，所以要融合。

## 练习

1. **推导.** 从 $\text{时间}=\max(\cdot,\cdot)$ 推出 $\text{MFU}\le\min(1,\text{算术强度}/\text{加速器强度})$。什么时候取等号？
2. **估算.** 一个 7B 参数的模型用 bf16 做推理，batch size 为 1，H100 上每生成一个 token 至少要多少时间？（提示：每步要把所有权重读一遍。）这时的 MFU 上界是多少？
3. **估算.** 把 $B=16$ 个 token 乘一个 $4096\times4096$ 的 bf16 权重。算术强度是多少？在 H100 上大约能跑到峰值的百分之几？
4. **思考.** 为什么 RMSNorm、softmax 这类运算在 Transformer 里 FLOPs 只占千分之一（[[02.4 训练的计算量为什么是 6ND]] §4.5），时间却可能占到可观的比例？这对写 kernel 意味着什么？

## 练习答案

1. 实际速度 = FLOPs/时间 = FLOPs/max(字节/带宽, FLOPs/峰值) = min(带宽 × FLOPs/字节, 峰值) = min(算术强度 × 带宽, 峰值)。除以峰值，得到 min(算术强度 × 带宽/峰值, 1) = min(算术强度/加速器强度, 1)。取等号需要两个理想条件：搬和算能完全重叠，并且除了这两项之外没有别的开销。
2. 权重 $7\times10^9\times2=1.4\times10^{10}$ 字节，除以 $3.35\times10^{12}$ 字节/秒，约 4.2 毫秒，也就是每秒最多约 240 个 token。每个 token 的 FLOPs 约 $2N=1.4\times10^{10}$，算术强度约 1，MFU 上界约 $1/295\approx0.34\%$。
3. $1/(1/16+2/4096)=15.9$，MFU 上界约 $15.9/295\approx5.4\%$。
4. 这些运算的算术强度很低，是带宽受限的。它们的时间由搬了多少字节决定，而每个运算都要把整个激活读一遍、写一遍，字节数和矩阵乘法的输入输出是同一个量级。所以它们的时间占比远高于 FLOPs 占比。写 kernel 时，要尽量把它们和相邻的运算融合起来，数据读进来一次就做完所有的事，再写回去。第 6 讲用 Triton 写 kernel，A2 写融合的 RMSNorm，都是为了这个。
