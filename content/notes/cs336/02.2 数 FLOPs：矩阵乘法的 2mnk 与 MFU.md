# 02.2 数 FLOPs：矩阵乘法的 2mnk 与 MFU

出处：CS336 第 2 讲（Percy Liang），`tensor_operations_flops` 一节；计时方法参考了第 6 讲的 `benchmarking`。所属栏目：[[notes/cs336/index|CS336：从零构建语言模型]]。文中的 GPU 实测数据取自课程 trace 里记录的值：第 2 讲是在 H100 上跑的，第 6 讲是在 B200 上跑的。

**术语预备**
- **FLOP / FLOPs / FLOP/s**：一次浮点加法或乘法 / 次数 / 每秒次数。前两个是工作量，最后一个是速度。FLOP/s 也常写作 FLOPS，很容易和 FLOPs 混淆，本栏目一律写 FLOP/s。
- **TFLOP/s**：$10^{12}$ FLOP/s。
- **峰值（peak）**：厂商规格表上的理论最高速度。真实程序达不到。
- **TF32**：NVIDIA 的一种 19 位格式（1 位符号、8 位指数、10 位尾数），专供 tensor core 处理 fp32 矩阵乘法用。
- **MFU（Model FLOPs Utilization）**：实际达到的 FLOP/s 除以峰值。

## 0. 问题：卡有没有跑满

估算训练时间要三个数：这次训练要做多少 FLOPs，硬件标称多快，实际能跑多快。第一个数见 [[02.4 训练的计算量为什么是 6ND]]。这篇讲后两个，以及把它们连起来的 MFU：怎么数、怎么读规格表、怎么计时才准，以及 MFU 为什么到不了 1。

## 1. 工作量：只数矩阵乘法

**矩阵乘法.** $A\in\mathbb R^{m\times n}$ 乘 $B\in\mathbb R^{n\times p}$，结果有 $mp$ 个元素，每个是长度为 $n$ 的内积：$n$ 次乘法，加上大约 $n$ 次加法。总共

$$2mnp\ \text{FLOPs}.$$

讲义的例子：$x\in\mathbb R^{16384\times32768}$ 乘 $w\in\mathbb R^{32768\times8192}$，$2\times16384\times32768\times8192=8.80\times10^{12}$ FLOPs。

**其他运算.** ReLU、加法、归一化这类逐元素运算，每个元素只要几个到几十个 FLOPs，总量是 $O(\text{元素个数})$。矩阵乘法是 $O(\text{元素个数}\times n)$，$n$ 是几千。所以算工作量时可以只数矩阵乘法。但要注意：FLOPs 少不代表耗时少，逐元素运算往往是最慢的那部分，原因见 [[02.3 算术强度与 roofline]]。

**量级感.** 讲义给了几个参照：
- GPT-3（2020）训练用了 $3.14\times10^{23}$ FLOPs。用 $6ND$ 验算：$6\times(175\times10^9)\times(300\times10^9)=3.15\times10^{23}$，对得上。
- GPT-4（2023）据传约 $2\times10^{25}$ FLOPs。
- 8 张 H100 跑两周，按 bf16 峰值算是 $9.6\times10^{21}$ FLOPs，大约是 GPT-3 的 1/33。

## 2. 标称速度：规格表怎么读

H100（SXM 版）规格表里和训练有关的几行：

| 数据类型 | 用不用 tensor core | 稠密峰值（TFLOP/s） | 规格表上的数 |
|---|---|---|---|
| fp32 | 不用 | 67 | 67 |
| TF32 | 用 | 495 | 989（带稀疏） |
| bf16 / fp16 | 用 | 989 | 1979（带稀疏） |
| fp8 | 用 | 1979 | 3958（带稀疏） |

有三点要注意。

**1. 带稀疏的数要减半.** 规格表上最醒目的数，是假设"每 4 个连续的权重里有 2 个是 0"这种结构化稀疏时的速度，硬件可以跳过那些 0。正常训练不用这种稀疏，所以要除以 2。讲义说 "1979 teraFLOP/s with sparsity, 50% without"，代码里写的就是 `1979e12 / 2`。

**2. 峰值取决于数据类型.** 同一块 H100，fp32 比 bf16 慢将近 15 倍。原因是 tensor core 只处理低精度输入，fp32 矩阵乘法走的是普通的计算单元。这是训练要用 bf16 的直接原因（[[02.1 浮点格式：为什么训练用 bf16]]）。

**3. "fp32" 矩阵乘法到底按哪个峰值算，取决于一个开关.** TF32 是一个折中：输入是 fp32，但进入 tensor core 前把尾数截到 10 位，累加仍用 fp32。用 TF32 的话，"fp32" 矩阵乘法的峰值就是 495 而不是 67。

课程里两种说法都出现了：
- 第 2 讲按 67.5 算。
- A1 handout 说 H100 的 "float32" 峰值是 495，括号里注明 "actually TensorFloat-32, which in reality is bfloat19"。

两者都对，取决于 PyTorch 是否允许用 TF32 做 fp32 矩阵乘法。PyTorch 默认不允许，调用 `torch.set_float32_matmul_precision("high")` 才会打开。第 2 讲 trace 里的实测值是 53.4 TFLOP/s，低于 67.5，说明当时跑的是真正的 fp32。如果用了 TF32，这个数会是几百。

## 3. 实际速度：怎么量才准

讲义的做法：把这个矩阵乘法跑几次，取平均时间，用 FLOPs 除以时间。H100 上的结果：

$$\frac{8.80\times10^{12}\ \text{FLOPs}}{0.1647\ \text s}=53.4\ \text{TFLOP/s}.$$

计时有两个坑，第 6 讲专门讲过：

**1. GPU 是异步的.** Python 里写 `y = x @ w`，CPU 只是把这个任务交给 GPU 排队，然后立刻往下执行，并不等 GPU 算完。如果直接用 `time.time()` 前后一掐，量到的只是"提交任务"的时间。所以计时前后都要调用 `torch.cuda.synchronize()`，它会让 CPU 等到 GPU 把手头的活全部做完。

**2. 第一次运行更慢.** 第一次调用时有一些一次性的开销，比如分配显存、挑选矩阵乘法用哪种实现。所以要先空跑几次（预热），再正式计时，并且多跑几次取平均。

第 6 讲的计时函数（加了中文注释）：

```python
def benchmark(run, num_warmups=1, num_trials=3):
    for _ in range(num_warmups):   # 预热：先空跑，把一次性开销排除掉
        run()
    torch.cuda.synchronize()       # 等预热真正跑完

    times = []
    for _ in range(num_trials):    # 多跑几次，看平均和波动
        start = torch.cuda.Event(enable_timing=True)   # 在 GPU 的任务队列里放一个计时标记
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        run()
        end.record()
        torch.cuda.synchronize()   # 等 GPU 跑到 end 这个标记
        times.append(start.elapsed_time(end))          # 两个标记之间的时间（毫秒）
    return sum(times) / len(times)
```

Python 要点：
- `run` 是一个函数，作为参数传进来，`run()` 才真正执行它。讲义里常用 `lambda: x @ w` 包一层，表示"一个无参数、调用时算 `x @ w` 的函数"。
- `torch.cuda.Event` 是 GPU 自己记录的时间点，比 CPU 上的 `time.time()` 更准，因为它不会把 CPU 那边的开销算进去。

## 4. MFU：实际速度占标称速度的比例

讲义的定义：

$$\text{MFU}=\frac{\text{实际 FLOP/s}}{\text{标称峰值 FLOP/s}}.$$

上面那次矩阵乘法：$53.4/67.5=0.79$。

用在一次完整的训练上，分子是"每秒处理的 token 数 × 每个 token 的模型 FLOPs"，也就是 $6N$ 加上注意力修正（[[02.4 训练的计算量为什么是 6ND]]），分母是"GPU 数 × 单卡峰值"。有两条惯例：
- **分子只数模型本身需要的计算.** 为省显存而重算的那一遍不算（[[02.6 梯度累积与激活重计算]]）。如果把它也算进去，得到的叫 HFU（Hardware FLOPs Utilization），会比 MFU 高。
- **分母用所用数据类型的稠密峰值.** 用 bf16 训练就除以 989，不能除以 1979，也不能除以 fp32 的 67。

讲义说 MFU 达到 0.5 就算相当好。为什么到不了 1？一个直接的证据是第 6 讲 trace 里的一组测量：在 B200 上做 $n\times n$ 的 fp32 矩阵乘法，峰值按 75 TFLOP/s 算。

| $n$ | FLOPs $2n^3$ | 时间（毫秒） | 实际 TFLOP/s | MFU |
|---|---|---|---|---|
| 256 | $3.4\times10^{7}$ | 0.744 | 0.045 | 0.06% |
| 512 | $2.7\times10^{8}$ | 0.699 | 0.38 | 0.5% |
| 1024 | $2.1\times10^{9}$ | 0.708 | 3.0 | 4% |
| 2048 | $1.7\times10^{10}$ | 0.756 | 22.7 | 30% |
| 4096 | $1.4\times10^{11}$ | 2.63 | 52.3 | 70% |
| 8192 | $1.1\times10^{12}$ | 17.65 | 62.3 | 83% |

讲义的评语是 "time is roughly constant when dimension is small, then cubic scaling"。$n\le2048$ 时时间几乎不变，都在 0.7 毫秒左右，说明这段时间花在和计算量无关的固定开销上，算本身只占很小一部分。矩阵要大到几千，计算量才能把固定开销摊薄，时间开始按 $n^3$ 增长，MFU 才上得去。

把 MFU 拉低的原因大致有三类：
1. **固定开销**，就是上表左半边的情况。
2. **等数据.** 运算太"稀"，GPU 大部分时间在等数据从显存搬过来，而不是在算。这是下一篇 [[02.3 算术强度与 roofline]] 的主题，讲义里 "MFU = min(1, arithmetic-intensity / accelerator-intensity)" 那句话就出自那里。
3. **等通信.** 多卡训练时，卡和卡之间要交换梯度和参数（第 7、8 讲）。

## 5. 用法：估算时间，或者反过来查自己的代码

**估算训练时间：**

$$\text{时间}=\frac{C}{\text{GPU 数}\times\text{单卡峰值}\times\text{MFU}}.$$

讲义开头的例子：$C=6.3\times10^{24}$，1024 张 H100，峰值 $989\times10^{12}$，MFU 取 0.5，算出来是 144 天。

**反过来查自己的代码.** 从训练日志里读出每秒处理多少 token，乘以 $6N$，再除以峰值，就是 MFU。如果只有百分之几，说明时间花在了别的地方：模型太小、数据加载太慢、逐元素运算太多，这时候应该去做 profile，而不是去调模型。[[02.4 训练的计算量为什么是 6ND]] 练习 1 里，A1 的 TinyStories 配置算出来大约是 1%。

## 6. 总表

| 要知道的数 | 怎么得到 | 常见的坑 |
|---|---|---|
| 工作量（FLOPs） | 只数矩阵乘法，每个 $2mnp$；训练约 $6ND$ | 逐元素运算 FLOPs 少，但不一定快 |
| 标称速度（FLOP/s） | 规格表上对应数据类型的稠密峰值 | 带稀疏的数要减半；fp32 是 67 还是 495，要看 TF32 开没开 |
| 实际速度（FLOP/s） | FLOPs ÷ 实测时间 | GPU 异步，要同步；要预热；要多跑几次 |
| MFU | 实际 ÷ 标称 | 分子不算重计算；0.5 已经很好 |

一句话：工作量数矩阵乘法的 $2mnp$，速度读规格表上对应数据类型的稠密峰值，计时要先预热、前后同步；两者之比就是 MFU。小矩阵、等数据、等通信，都会让它离 1 很远。

## 练习

1. **读规格表.** 有人用 H100 训练 bf16 模型，汇报 MFU 是 30%，事后发现他的分母用的是 1979 TFLOP/s。真实的 MFU 是多少？
2. **估算.** 按第 6 讲那张表，$n=8192$ 时 MFU 是 83%。把同样的矩阵乘法改成 bf16，在 B200 上（bf16 稠密峰值 $2.25\times10^{15}$ FLOP/s）要达到同样的 MFU，时间应该是多少？实际会更容易还是更难达到？
3. **找错.** 下面的计时代码错在哪里？量出来的数会偏大还是偏小？
   ```python
   t0 = time.time()
   y = x @ w
   t1 = time.time()
   print(2 * m * n * p / (t1 - t0))
   ```
4. **估算.** A1 的 `adamw_accounting` (d) 问：H100、TF32 峰值 495 TFLOP/s、MFU 50%、batch size 1024，训练 GPT-2 XL 40 万步要多久。不用算出结果，只说清楚：需要哪几个数，各自从哪里来。

## 练习答案

1. 稠密峰值是 989，他的分母大了一倍，真实 MFU 是 $30\%\times1979/989\approx60\%$，其实相当好。
2. $1.1\times10^{12}/(0.83\times2.25\times10^{15})\approx0.59$ 毫秒，比 fp32 的 17.65 毫秒快 30 倍。实际上更难达到：同样大小的矩阵，算得快了 30 倍，但要搬的字节只少了一半，固定开销也不变，所以计算更难把这两样摊薄。要达到同样的 MFU，矩阵得更大。下一篇会把这一点量化。
3. GPU 是异步的，`y = x @ w` 只是把任务提交出去，`t1 - t0` 量到的是提交时间，远小于真实计算时间，所以算出的 FLOP/s 会严重偏大，可能超过峰值。另外第一次运行还包含一次性开销，这一项会让时间偏大。两个误差方向相反，单次测量没有意义。正确做法见 §3。
4. 需要每一步的 FLOPs 和总步数。每一步的 FLOPs = 每个 token 的训练 FLOPs（题目给了"反向是前向的 2 倍"，所以是 3 倍的前向 FLOPs，前向 FLOPs 用 `transformer_accounting` 算出来的值）× 每步的 token 数（$1024\times1024$，batch size 乘 context length）。再除以 $495\times10^{12}\times0.5$，得到秒数。
