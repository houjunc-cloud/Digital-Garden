# 03.8 GQA 与 MQA：为 KV cache 省显存

出处：CS336 第 3 讲（Tatsu Hashimoto），第 57–63 页。所属栏目：[[notes/cs336/index|CS336：从零构建语言模型]]。计时在本地 CPU 上测。

**术语预备**
- **自回归生成**：一次生成一个 token，生成出来的 token 接到输入末尾，再生成下一个。
- **KV cache**：生成时把之前所有 token 在每一层算出的 $k$、$v$ 存下来，下一步直接用，不必重算。
- **MHA（multi-head attention）**：标准多头注意力，每个头有自己的 $W_Q,W_K,W_V$。
- **MQA（multi-query attention）**：所有头各有自己的 $q$，但共用**一份** $k$、$v$。
- **GQA（grouped-query attention）**：把 $h$ 个头分成 $G$ 组，每组共用一份 $k$、$v$。$G=h$ 是 MHA，$G=1$ 是 MQA。

## 0. 问题：注意力头还有什么可改的

讲义第 57 页："Most models don't touch the attention heads much at all with a few minor exceptions"。例外有三类：GQA/MQA（降低推理成本）、稀疏或滑动窗口注意力（降低长序列的计算量，见 [[03.9 滑动窗口与全局、局部交错注意力]]）、以及状态空间模型这类更激进的替代（第 4 讲）。

这篇讲第一类：为什么推理时注意力成了瓶颈，以及 MQA、GQA 怎么用很小的代价解决它。

## 1. 训练时，注意力不缺算力

讲义第 58 页的记号：$b$ 是 batch，$n$ 是序列长度，$d$ 是宽度，$h$ 是头数，$k=d/h$ 是头维度。训练时一次处理全部 $n$ 个 token：
- 计算量约 $bnd^2$（投影矩阵乘法为主）。
- 读写量约 $bnd+bhn^2+d^2$（激活、注意力矩阵、权重）。

算术强度是 $O\big((1/k+1/(bn))^{-1}\big)$，很高，"we can keep our GPUs running"。这和 [[02.3 算术强度与 roofline]] 的结论一致：一次喂进去成千上万个 token，矩阵乘法够大。

## 2. 生成时：KV cache 成了瓶颈

生成时只能一个一个地来（第 59 页："can't parallelize the generation process"）。每生成一个 token，新 token 的 $q$ 要和之前所有 token 的 $k$ 做点积，再对它们的 $v$ 加权求和。之前那些 $k$、$v$ 不变，所以存在 KV cache 里。

### 2.1 缓存有多大

每个 token、每一层要存一份 $k$ 和一份 $v$，各有（KV 头数 × 头维度）个数：

$$\text{每 token 的 KV cache}=2\times L\times n_{\text{kv}}\times d_{\text{head}}\times(\text{每个数的字节}).$$

按 bf16 算几个真实模型：

| 模型 | 层数 | KV 头数 | 每 token | 4K 上下文 | 128K 上下文 |
|---|---|---|---|---|---|
| Llama 2 7B（MHA） | 32 | 32 | 512 KB | 2 GiB | 64 GiB |
| Llama 2 70B（GQA，8 组） | 80 | 8 | 320 KB | 1.25 GiB | 40 GiB |
| 假如 Llama 2 70B 用 MHA | 80 | 64 | 2.5 MB | 10 GiB | 320 GiB |
| Llama 3 8B（GQA，8 组） | 32 | 8 | 128 KB | 0.5 GiB | 16 GiB |

这是**每条序列**的量。同时服务很多用户时，缓存很容易比模型权重还大。

### 2.2 为什么它决定速度

讲义第 60 页算了生成过程的算术强度。为 $b$ 条序列各生成 $n$ 个 token：
- 计算量约 $bnd^2$。
- 读写量约 $bn^2d+nd^2$：第一项是每一步都要读整个 KV cache（第 $t$ 步读 $t\cdot d$，累加起来约 $n^2d/2$，每条序列各一份）；第二项是每一步都要把权重读一遍。

算术强度是

$$O\Big(\big(\tfrac nd+\tfrac1b\big)^{-1}\Big).$$

$1/b$ 那一项可以靠加大 batch 压下去，这是 [[02.3 算术强度与 roofline]] §3 说的"把很多请求拼成一个 batch"。但 $n/d$ 那一项和 batch 无关：**每条序列有自己的缓存，batch 再大也摊不薄。** 上下文一长（$n$ 比 $d$ 大），算术强度就掉到 1 以下，GPU 绝大部分时间在等缓存从显存里读出来。讲义的原话是："The n/d term is difficult to reduce"。

## 3. MQA 与 GQA：少存几份 K、V

**MQA**（第 61 页，Shazeer 2019）："have multiple queries, but just one dimension for keys and values"。每个头还有自己的 $q$，但 $k$、$v$ 只有一份，所有头共用。缓存缩小 $h$ 倍，读写量变成 $bnd+bn^2k+nd^2$，算术强度变成

$$O\Big(\big(\tfrac1d+\tfrac{n}{dh}+\tfrac1b\big)^{-1}\Big),$$

麻烦的那一项被除了 $h$。

**GQA**（第 62 页，Ainslie 等人 2023）："Don't go all the way to one dimension of KV – have fewer dims"。把头分成 $G$ 组，每组一份 $k$、$v$，缓存缩小 $h/G$ 倍。$G$ 是一个旋钮，一头是表达能力（MHA），一头是推理效率（MQA）。Llama 2 70B、Llama 3 都是 8 组。

**实测：同样的 FLOPs，时间跟着缓存走.** 在 CPU 上模拟一步生成：batch 4、上下文 4096、16 个头、头维度 128，只改 KV 头数：

| KV 头数 | 缓存 | 一步的时间 |
|---|---|---|
| 16（MHA） | 256 MB | 15.5 ms |
| 4（GQA） | 64 MB | 7.2 ms |
| 1（MQA） | 16 MB | 2.9 ms |

三种情况的 FLOPs 完全一样（16 个 $q$ 都要和 4096 个 $k$ 做点积），时间却差了 5 倍多。缩小 16 倍的缓存没有换来 16 倍的加速，是因为缓存小了以后，softmax 等其他开销开始占比例，但主趋势很清楚：生成速度由缓存的大小决定。

## 4. 代价：效果掉多少

讲义第 63 页的标题是 "Does MQA hurt? Sometimes.."。

**MQA 有一点损失.** Shazeer（2019）的实验（Billion-Word 基准上的困惑度，越低越好）：

| 注意力 | 头数 | $d_k,d_v$ | $d_{ff}$ | 困惑度 |
|---|---|---|---|---|
| MHA | 8 | 128 | 8192 | 29.9 |
| MQA | 8 | 128 | 9088 | 30.2 |
| MHA，单头 | 1 | 128 | 9984 | 31.2 |
| MHA，8 个小头 | 8 | 16 | 9984 | 30.9 |

（MQA 少了 K、V 的参数，用加大 $d_{ff}$ 补齐。）MQA 只比 MHA 差 0.3，比"把头变少或变小"来省缓存的办法好得多。

**GQA 几乎没有损失.** Ainslie 等人的结果：GQA 的效果接近 MHA，速度接近 MQA。他们画的"每个样本的推理时间对分组数"的曲线，在 8 组以内几乎和 MQA 一样，16 组开始上升，到 64 组（即 MHA）陡升。

讲义第 62 页还提到 DeepSeek V2 的 MLA（multi-head latent attention）：不是减少 KV 头数，而是把 $k$、$v$ 压缩成一个低维的潜向量再缓存。它和 RoPE 的配合比较麻烦（[[03.4 位置编码：正弦编码到 RoPE]] §3），细节在 [[10.3 缩小 KV cache：GQA、MLA、跨层共享、局部注意力]]。

## 5. 实现

```python
# x: (B, n, d)；Wq: (d, h*dh)；Wk, Wv: (d, G*dh)；h 个 query 头，G 组 KV
q = (x @ Wq).view(B, n, h, dh).transpose(1, 2)          # (B, h, n, dh)
k = (x @ Wk).view(B, n, G, dh).transpose(1, 2)          # (B, G, n, dh)：只有 G 份
v = (x @ Wv).view(B, n, G, dh).transpose(1, 2)
k = k.repeat_interleave(h // G, dim=1)                  # 每份复制给组里的 h/G 个头
v = v.repeat_interleave(h // G, dim=1)                  # 之后就和普通 MHA 完全一样
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
```

缓存里只存复制前的 `k`、`v`。我核对过：GQA 的结果和"把 K、V 复制之后的 MHA"相差 $10^{-7}$，即两者在数学上相同。高效的实现不会真的去复制，而是把 $q$ 改成形状 $(B,G,h/G,n,d_{\text{head}})$，让同组的头直接共用同一份 $k$、$v$。

Python 要点：
- `repeat_interleave(r, dim=1)` 把第 1 维的每个元素原地重复 $r$ 次：`[a, b]` → `[a, a, b, b]`。用它而不用 `repeat`，是为了让相邻的头属于同一组。
- `F.scaled_dot_product_attention` 是 PyTorch 内置的注意力，会自动选用 FlashAttention 一类的高效实现。A1 要求自己写，这里只是示意。

**参数的变化.** $W_K$、$W_V$ 从 $d\times d$ 缩成 $d\times(G\cdot d_{\text{head}})$。Llama 2 70B 里是 $8192\times1024$，只有原来的 1/8。省下的参数可以补给 FFN。Llama 2 70B 的 $d_{ff}/d=3.5$，比 LLaMA 1 65B 的 2.69 大，可能就有这个原因（[[03.5 超参数的共识：FFN 倍数、头维度、宽深比、词表大小]] §1）。

## 6. 总表

| | MHA | GQA（$G$ 组） | MQA |
|---|---|---|---|
| KV 头数 | $h$ | $G$ | 1 |
| KV cache | $2Lhd_{\text{head}}$ / token | 缩小 $h/G$ 倍 | 缩小 $h$ 倍 |
| 训练计算量 | 基准 | 略少（K、V 投影变小） | 略少 |
| 生成速度 | 基准，长上下文时被缓存卡住 | 快几倍 | 最快 |
| 效果 | 基准 | 几乎不变 | 略差 |
| 谁在用 | Llama 2 7B/13B、GPT-3 | Llama 2 70B、Llama 3、Mistral 等 | PaLM |

一句话：逐个生成 token 时，每一步都要把整个 KV cache 读一遍，而且每条序列各读各的，所以长上下文的生成被缓存的大小卡死；MQA、GQA 让多个 query 头共用一份 K、V，缓存小几倍到几十倍，效果几乎不掉，这是推理时最划算的一笔交易。

## 练习

1. **估算.** Llama 3 70B（80 层、8 个 KV 头、头维度 128、bf16）每 token 的 KV cache 是多少？8 张 80 GB 的 H100 放下 140 GB 的 bf16 权重以后，剩下的显存能放几条 128K 长的序列？
2. **推导.** 按 §2.2 的思路，推出讲义第 60 页的算术强度 $O((n/d+1/b)^{-1})$。哪一项来自 KV cache，哪一项来自权重？
3. **思考.** GQA 在训练时能省多少计算？为什么它主要是一个推理优化？

## 练习答案

1. $2\times80\times8\times128\times2=327680$ 字节，即 320 KB。128K 上下文是 40 GiB（约 43 GB）。640 GB 减去 140 GB 剩 500 GB，大约能放 11 条（不算激活等其他开销）。
2. 计算量：每条序列每个 token 过一遍所有投影，约 $d^2$ 量级，共 $bnd^2$。读写量：KV cache 第 $t$ 步读 $t\cdot d$，$n$ 步累计约 $n^2d$，$b$ 条序列共 $bn^2d$；权重每一步都要读一遍，$n$ 步共 $nd^2$，与 batch 无关。相除得 $bnd^2/(bn^2d+nd^2)=1/(n/d+1/b)$。$n/d$ 来自 KV cache，$1/b$ 来自权重。
3. 训练时 GQA 只把 $W_K$、$W_V$ 两个投影变小，每层省下约 $2d(d-Gd_{\text{head}})$ 个参数对应的计算，相对整层的 $12d^2$ 不到六分之一，而且这部分往往又补给了 FFN。训练是算力受限的，一次处理全部 token，没有 KV cache 的读写问题。GQA 真正的收益在生成时：缓存小了，每一步要读的字节少了。
